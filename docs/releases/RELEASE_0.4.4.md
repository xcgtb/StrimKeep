# 0.4.4：修正已回收文件的存续误判

后续实测：原 #10 已整理 1、Emby 接受通知；空目录回收类型仍未识别，批次部分完成。目录 type=2 和单独恢复入口见 [0.4.5](RELEASE_0.4.5.md)。以下保留本版历史说明。

2026-10-23。用户升级 0.4.3 后，原任务 #10 仍等待核查，提示“已记录回收的文件仍存在或被恢复/移动”。本次只修正这个存续检查及相关回归，不合入下一阶段的分类或扫描优化。

## 真实接口证据

用户在同一账号、同一个原文件 ID `3546307877859755390` 上执行只读检查：

| 查询 | 实际结果 |
|---|---|
| `fs_file_skim` / `GET /files/file` | `state=true`，仍返回原文件 ID、名称、精确字节数 `15177603331`、pick_code、sha1；没有 aid/area_id |
| `fs_file` / `GET /files/get_info` | `state=false, code=20018`，没有 data |

0.4.3 使用第一个接口判断是否仍存续，并把缺失 aid 默认成 1，错误地把回收后的元数据判为正常网盘文件。上轮解决的是回收记录 ID 与原文件 ID 混淆，未解决这一独立错误；不是用户操作、媒体库权限或定时清空造成的。

## 修正

- 视频、重复副本、字幕和任务空目录共用的存续检查改为详情接口；只将 SDK 明确识别的不存在错误（含真实 `code=20018`）判断为不存续。
- 成功响应核对准确 ID、普通文件/目录 ID 字段及明确 aid/area_id，不再默认缺失状态。恢复或移到其他位置的正常原文件仍会阻止收尾。
- 登录、网络、未知错误、缺失字段或矛盾状态不当作已回收。未知成功结构继续停止核查。
- 原有回收记录唯一关联、请求前快照/旧意图时间证据、原目录无该 ID、保留新版本及 STRM 校验全部保留。详情接口返回不存在，本身不能单独证明本次回收成功。
- 已提交的回收意图继续只读核查，不再次发送回收；已确认并落库的证据仍可在回收站后来清空后复用。

## 更新和恢复原任务 #10

解压到 `/path/to/StrimKeep-v0.4.4-livecheckfix` 后：

```bash
cd '/path/to/StrimKeep-v0.4.4-livecheckfix/StrimKeep' &&
bash update.sh '/path/to/StrimKeep-v0.1.0-phase1/StrimKeep'
```

沿用原账号、Cookie、数据库、master.key、Token、数据和 STRM 挂载；无数据库结构变更。预编译前端随包提供，NAS 不运行 npm。

1. 保留任务 #10 的回收站条目和现有云端、本地文件；无需复制另一批视频，不取消原任务。
2. 确认服务启动日志或 Web 显示 0.4.4，在原 #10 点“核查并继续”。
3. 核查通过后，预期任务完成、2160p 云端文件去除 `.sknew` 后缀、旧 1080p STRM 清除和旧 Token 撤销、新 2160p STRM 保留，并按原设置通知 Emby。再验证 Emby 入库和播放。
4. 若仍等待核查，保留具体提示与文件步骤；不要用重建任务或手动改数据库覆盖现场。
