# 0.4.0：第四阶段洗版与多版本共存

2026-10-23。依据 StrimKeep V1.1 第 5、6、12 节开发。沿用已验证的索引、识别、探测、改名、移动、字幕、STRM、Emby 链路。0.3.1 更新后直接检查登录、再次重启后直接检查登录，用户均反馈通过；不将该结果扩展为所有执行中重启用例均已通过。

## 使用入口

新增左侧“洗版管理”。保存规则后，在“扫描整理”启动新任务；每个任务保存配置快照，正在运行的任务不会跟着设置变化。

初始为“冲突进待处理”，比较规则全部关闭；更新本身不会启用淘汰。可选择：

| 模式 | 同片/同集时的行为 |
|---|---|
| 冲突进待处理 | 保留旧版，新副本原名转待处理，沿用原基线 |
| 已有冲突直接跳过 | 不探测已确认的冲突，不改新旧文件，记录原位置跳过 |
| 允许洗版 | 先分共存组，再按已启用规则逐项比较 |

“只读检查回收站接口”只检查登录、回收站完整分页与必要字段，不回收任何文件。启用洗版的后台任务在任何分类/源文件修改前也先检查该接口；接口格式、分页、登录或网络无法核实时停止。

## 比较与共存

- 十项规则均可启停、上移/下移：发布组、资源类型与平台、分辨率、动态范围、帧率、色深、音频、修订版本、编码、文件大小。
- 文字规则需明确输入偏好，按列表由优到次。未列入偏好、未知、缺关键字段时不能继续跳到大小规则。数值规则可配置较大或较小优先。全部已启用规则相同则新副本待处理。
- 已有资源按需实际 FFprobe；原始名称取已确认的历史整理记录，无法获取时只解析当前名称明确可见的字段。探测后和回收前再次核查 ID、名称、大小、SHA1、父目录及范围。
- 实测分辨率兼顾 3840×1600、1920×800 等裁切画面；帧率保留原有理数，比较时归一化 23.976/59.94/119.88。动态范围未知不默认 SDR；明确 8-bit 像素格式可作为实测色深依据。保留音轨 profile、声道等；按用户编码偏好与声道选代表轨，未知 DTS profile 不自动当作普通 DTS。
- 分辨率、动态范围、帧率可组合分组；组键仅含启用维度。未知帧率放低档只用于兼容展示，不足以授权同组淘汰。
- 不同组分别保留。同一作品的合并集与单集仅覆盖重叠、范围不一致时转待处理，不互相淘汰。
- 标准剧集目录仍为 `作品/Season 1`，版本标记写入 `剧名.年份 - S01E01 - 版本组.技术参数.strm`。规格季目录另有 `Season 1 - 版本组` 选项，明确标为需 Emby 实测；本地结构测试不证明播放器兼容。电影共存名以作品目录名开头，再加版本标记。

## 替换顺序与恢复

更优版本使用含源文件 ID 的临时唯一名归档，不先删除旧版腾位置。新视频、外挂字幕、STRM、有效 Token 及本地输出校验通过后，才按记录逐个回收旧视频和明确绑定的旧字幕。每个回收意图先持久化；只调用单文件 `fs_delete`，不删作品/季目录，不调用回收站永久清理。

回收完成须取得匹配文件 ID、名称、大小的回收站记录，并完整核对原父目录中已无该 ID。响应丢失/进程中断后先核查；有正面证据可补提交完成标记，没有证据就等待核查，绝不盲目重复发送回收。回收记录 ID 显示在文件步骤中，可在 115 回收站人工还原。本版的“恢复”指中断核查续作，没有提供自动批量还原按钮。

新版本更差时，先重新核实已有优质版，再回收新副本及明确关联的新字幕；旧版不动。同分、关键字段不足、身份或目录变化均保留旧版，按待处理/核查状态停止淘汰。

洗版完成后撤销旧映射，只清理由程序记录、路径受限且哈希一致的旧 STRM/字幕；同名的新输出保留。已修改的旧本地文件保留并记录警告。旧版记录没有字幕哈希时保留其本地字幕；如果与新字幕同路径且不能核实归属，停止覆盖并要求核查。NFO、海报、背景图及用户其他文件不清理。

任务取消不回滚已完成动作；新文件可能处于记录中的临时名，需按任务状态核查。“补齐已归档输出”只读核查云端并写本地，不会继续取消任务里的回收或改名。旧映射已被其他有效版本接管路径时，禁止重新生成旧 Token 覆盖新 STRM；有效映射正常更新 Token 时也更新输出哈希记录。

## 界面提示修正

网络断开或反代返回不可解析内容时，用中文提示恢复后先核实操作结果。自动轮询失败显示为状态读取警告，成功读取后自动消除；不会仅凭网页连接错误宣称任务失败。

## 更新

先等当前任务完成。解压至 `/path/to/StrimKeep-v0.4.0-phase4`：

```bash
cd '/path/to/StrimKeep-v0.4.0-phase4/StrimKeep' &&
bash update.sh '/path/to/StrimKeep-v0.1.0-phase1/StrimKeep'
```

沿用原 .env、数据、密钥、Cookie、Token、挂载和 Emby 路径。0.3.1 升级不改变数据库表结构，配置使用原有加密 settings，洗版动作及证据使用原有 organize_items.plan。不自动备份或重建数据库。继续使用预编译前端，NAS 不运行 Node/npm。

## 真实 NAS 验收顺序

先使用独立、可恢复的小批测试副本，不能直接拿整库做自动淘汰验收。

1. 更新 Healthy、页面 0.4.0；直接检查 115 登录通过，旧任务/目录配置仍在。
2. “洗版管理”先保持冲突待处理，点击“只读检查回收站接口”。不通过就先反馈提示，不进入自动洗版。
3. 接口通过后，测试允许洗版，仅启用“分辨率”、较大优先，先关闭共存。相同实测分辨率的重复副本应同分待处理；原版保留。
4. 准备同片/同集实际 1080p 和 2160p 副本：先归档 1080p，再整理 2160p，预期新版本与输出就绪、旧版入回收站、新版本最终命名、旧入口撤销，Emby/Senplay 实际播放新资源。反向测试应仅回收较差的新副本。
5. 测缺少已启用关键字段，预期待处理；测合并集部分重叠，预期保留旧版、不淘汰。
6. 启用分辨率共存，再测 1080p/2160p，预期两版均在、不回收，核实实际 Emby 与 Senplay 版本选择。标准 Season 先验收，规格季目录单独测试，未通过不得宣称兼容。
7. 在新文件临时归档、输出发布、回收后最终命名前分别测暂停/继续与重启；确认无重复回收、重复移动。无法确认回收结果时应等待核查。
8. 测字幕下载失败、Token 撤销、本地新输出被移走：旧版应保留；恢复后核查继续。取消后补齐输出应没有云端写操作。

完整 STRM 同步、定时、多个任务的 FIFO 排队、站内推送与 Telegram 留在第五阶段。NFO/图片 Web 开关、ISO、GitHub/GHCR 仍延期。

## 验证范围

本地使用真实固定版本 SDK 搭配受控 HTTP/网盘替身核对协议与恢复流程，没有使用用户 115 账号。本地测试不等于真实回收站接口及 Emby/Senplay 兼容已通过；以本轮 NAS 验收为准。没有本地 Docker 或可用浏览器内核，容器构建和浏览器视觉交互不能标记为本地已验证。
