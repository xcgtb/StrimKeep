# StrimKeep 0.5.5：115 转存与 Telegram 交互

2026-10-24。在 0.5.4 自动整理修复基础上，增加 Web/TG 转存入口与作品海报、STRM 信息通知。仍为单容器、现有串行 FIFO；不修改既有洗版规则或数据库表结构。

## 从提供的日志学习了什么

日志来自另一个工具的实际运行，不是本项目的验收记录。采用其中清楚的交互顺序：接收任务 → 转存结果 → 后续整理 → 按作品汇总 → STRM 批次结果 → 分批文件明细。相同作品同季合并海报和本批实际集数；无新增 STRM 的同步不重复发送媒体明细。不照搬日志中展示的扫描速度，也不把别的工具运行成功当作本项目已实测。

## Web 转存

侧栏新增“115 转存”，手机在“更多”中进入。

1. 选择目标目录并保存。目标必须是非根目录。
2. 粘贴 `https://115.com/s/分享码?password=提取码` 等 115 分享链接，也接受“提取码：abcd”的文本。支持 115.com、115cdn.com、anxia.com；一次最多 10 个链接。
3. 点“开始转存”。进度和结果显示在本页及统一任务队列。
4. 每个任务在所选目录下创建独立“转存任务-编号”子文件夹，避免与已有文件夹合并或覆盖。
5. 可开启“转存后自动整理”。此时目标必须是已保存的待整理目录之一；转存完成后自动创建整理任务，扫描该待整理目录、归档、生成 STRM，并按原设置通知 Emby。该目录已有待整理内容也会被处理。

转存前先记录分享内容与目标，提交前持久化意图。收到错误或响应丢失时，恢复只核查实际保存的目录树、文件名、类型和大小，不重复提交。已确认结果才创建后续整理任务，后续任务与父任务关联一起保存，避免重启重复排队。账号或目录改变、分享不完整或结果有歧义时停止核查。

## TG 机器人设置和操作

1. 在“通知与消息”启用 Telegram，保存 Bot Token 和通知 Chat ID，先发送一次测试通知。
2. 在“115 转存”保存默认目标目录，按需要选择自动整理；填入允许发起转存的 TG 用户数字 ID，开启“转存机器人”并保存。
3. 若通知 Chat ID 是正数私聊用户 ID，页面会预填该值供核对；通知目的地是群/频道时，须另外填写操作者自己的正数用户 ID。
4. 等页面显示“机器人已连接”后，再私聊机器人发送新的分享链接。

| 发送内容 | 行为 |
|---|---|
| 分享链接及可选提取码 | 保存到 Web 配置的默认目录 |
| `/save 目录ID 分享链接` | 保存到指定目录；自动整理开启时仍须是已配置的待整理目录 |
| `/help`、`/start`、`/status` | 显示当前使用方法 |

链接可以在正文、图片说明中，也可以是正文/说明内的隐藏超链接。机器人只接受授权数字用户 ID 的私聊命令；群内消息、其他用户或 Bot 发来的链接不会创建转存任务。

接收用 Bot API 长轮询，无需给 NAS 开放接收端口。首次开启或重新开启会忽略启用前的积压消息，只处理新消息。消息游标和对应转存任务记录持久化；同一条消息重放不会重复创建任务。

同一个 Bot Token 应只交给一个程序接收消息。若已有其他程序使用 getUpdates 或 webhook，请为本工具另建 Bot，或停止其他程序的接收；本工具不会自动移除已有 webhook。接收失败时页面提示连接错误，并不会假装仍可接收。

## 海报与 STRM 通知

Telegram 通知开启后，整理产生有效 STRM 时自动发送：

- 作品海报（TMDB 有可用海报时），标题、年份、当前季与本批实际集数范围。
- 来源、分类、版本、文件数、总体积、TMDB 编号与 STRM 目录。
- Emby 已接受扫描时显示“已通知扫描”，不把接受请求当成已完成实际入库。
- STRM 批次汇总及文件路径明细。每条最多 20 个文件；消息较长时进一步拆分，52 个普通路径会分成 3 条。

没有海报时发送文字；Telegram 明确拒绝海报时降级文字。发送结果不明不重复推送，通知记录保留。STRM 明细发送相对文件路径，不发送播放 Token 或临时直链。消息发送串行限速，并用持久化事件键去重，不阻塞整理和调度。

## 建议验收顺序

1. 先 Web 保存一个小分享，关闭自动整理，确认所选目录下的任务子文件夹及全部内容。
2. 用自己的 TG 私聊发送另一个测试链接，确认收到任务编号，且保存到默认目录。
3. 用 `/save 目录ID 分享链接` 验证指定目录。重启后确认同一消息不重复保存。
4. 开启自动整理，用一部电影或少量剧集确认“转存完成 → 整理任务入队 → STRM → Emby 通知”的链路。
5. 核对 TG 海报、作品信息、实际集数与 STRM 明细；检查实际播放和 Emby 入库。

## 已验证与真实环境边界

- 完整后端回归 299 项通过；随后最终转存专项 14 项通过，覆盖授权/CSRF、提取码解析、分享 SDK 请求契约、消息重放与游标、缺失内容恢复、转存响应丢失、后续整理只入队一次、海报合并、52 集分批通知和敏感信息遮蔽。
- 前端 7 项测试与 TypeScript/Vite 构建通过。受控浏览器实际走通侧栏、目录选择、保存、提交、真实本地 Worker 执行、历史结果；375/390/768/1440 宽度无横向溢出。测试环境没有中文字库，不把该环境的字体外观当作手机字体验收。
- 本地测试使用受控 115 与 Telegram 响应，未使用用户真实 Cookie、Token 或分享内容；没有实际向用户 TG 发消息。真实分享保存、Bot 收发、图片展示及 Emby 播放仍需上述验收。
- 提供的原始日志包含个人信息，未打包进入发布文件。新分享码和提取码加密保存在设置中，不进入公共任务响应或操作日志。

协议参考：[Telegram Bot API](https://core.telegram.org/bots/api)；115 分享接口按当前固定 p115client SDK 的 share_snap/share_receive 源码与受控 HTTP 回放实现，未宣称完成真实 115 契约验收。
