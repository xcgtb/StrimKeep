# StrimKeep：按实际运行修订计划（0.5.6）

2026-10-24。依据包内《StrimKeep 项目立项与执行计划 V1.1》、本轮代码及用户实际反馈对照。计划用于约束目标，不要求为了完成条目而保留低效流程；“源码已有”“受控测试通过”和“真实 NAS 验收通过”分开记录。本表是原计划的执行补充，原 Word 保留作为历史需求记录。

## 计划中已经调整的设计

| 原计划 | 实际反馈与当前处理 |
| --- | --- |
| 初次必须建立归档索引，索引不完整先处理索引 | 已取消日常整理的强制盘点前置。本地记录自动更新，现场检查相关作品；旧库盘点仅用于发现非标准、未登记旧资源。用户无需维护文件 ID 关联。 |
| 每次同步都完整遍历，再逐文件反复查询 | 手动完整核对；定时在 30 分钟内复用有效清单，本程序云端修改立即使缓存失效。完整读取时，身份、内容指纹、路径和本地输出均未变化的文件跳过详情复查。不是实时事件监听。 |
| Emby 失败或超时永不重试 | 改为每批最多 3 次扫描尝试，重试前先查本批 STRM 是否已入库；后台检查最长 30 分钟，不阻塞整理队列。扫描响应与实际入库状态分别显示。 |
| 动画电影归动漫 | 按后续确认修正：动画电影按地区归电影；动画剧集保留动漫与季目录。一次性历史搬迁功能已撤下，不再靠专用脚本迁移旧库。 |
| 为所有状态增加设置与操作按钮 | 不再据此扩展界面。主要操作和必要反馈应直接可见；整体 UI 重做仍未完成，不能把布局已有当作易用性通过。 |
| 修订版本列为独立洗版规则 | 当前按后续版本保留九项比较，V 标记仍可保留在名称；不为恢复历史表格擅自增加第十项。 |

## 接下来的改进顺序

1. **先验收当前主链路**：一个小分享、一部电影、少量剧集，核对本批范围、实际云端位置、STRM、字幕、Emby 指定版本和 TG 信息。异常时自动重试有界，文件结果不明仍禁止重复回收。
2. **播放协调**：在不增加云端 API 并发、不改变后台 FIFO 的前提下，让播放请求在单次 API 边界优先取链；实测长扫描时起播、拖动、续播。
3. **UI 重整**：整理、同步、转存各一条清楚流程；默认只显示结果和可执行操作，技术字段进入详情。统一术语，减少多层折叠和例行提示。
4. **大库与长运行**：先记录目录数、文件数、请求数、扫描耗时和队列等待，再决定目录级增量或事件机制。补齐失败恢复、迁移和记录归档；长期审计不等于永远堆在热表里。
5. **进阶能力**：在本地主链路和回归通过后推进 GitHub/GHCR 发布、自动更新提示、TG 任务查询/操作和更细的转存选择。按使用频率逐项做。

ISO、本地 NFO/图片写入、多网盘、视频代理兜底仍延期。TG 使用 TMDB 海报不代表已实现本地海报管理；程序仍优先采用 302，不下载视频做代理。

## 真实验收的完成口径

阶段五的功能实现已覆盖多数条目，但 T07、T11、T12、T15 及长期运行证据不全，不能把第五阶段全部验收或第六阶段完成写成既成事实。用户已通过的具体样本保留有效；没有证据的场景保持“待实测”。下一阶段应围绕这些缺口补验证和改进，版本号不代替验收结论。
