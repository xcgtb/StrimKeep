# 115 请求节奏与风控预案

> 结论先行：StrimKeep 从第一版起就是「全局串行 + 最小间隔」，不存在并发批量移动；
> 从 0.7.0 起读写分档、写操作用更慢的间隔，并能在被限流时自动降速、冷却、停下整批。

## 1. 现在的真实行为

所有 115 API 调用都走 `Cloud115.call()`，同一个 `asyncio.Lock` 串行，调用之间按类型留最小间隔：

| 类型 | 默认间隔 | 说明 |
| --- | --- | --- |
| 读（列目录、详情、取直链） | 350 ms | `cloud_throttle.read_ms` |
| 写（移动、重命名、新建目录、删除、恢复、转存） | 3000 ms | `cloud_throttle.write_ms` |
| 播放取链 | 50 ms | 独立门，只影响播放地址刷新；0.9.57 起是**有限并发 4 路**，见下 |

播放取链（`playback_request` 为真的调用）单独走一道门：0.9.57 之前它是一把全局
`asyncio.Lock`，间隔和请求被同一把锁扣住，N 个并发请求要等前 N-1 个跑完
（`N ×（50ms + 往返）`）。实测单个 302 只要 0.21 秒，但 6 个并发要 1.37 秒。
现在换成 `Semaphore(Cloud115.PLAY_CONCURRENCY = 4)`：请求可以同时在飞，
「发车时刻」由 `reserve_play_slot()` 在一把单独的锁里原子预留，仍是每 50ms 一发
（≤20 次/秒），对 115 的实际压力与改前一致，只是不再把播放器的并发突发排成串行。

写操作额外有一道「突发保险丝」：连续写 `burst`（默认 15）次后，主动暂停 `pause_ms`（默认 30 秒）。

所以「秒移动」在代码层面不可能发生：61 个文件的批量整理，写操作至少按 3 秒一个走，
再加每 15 次一次的 30 秒暂停，一批 60 次写最少 3 分钟以上。

离线目录的兜底扫描（0.8.40 起）也走这套读节流：`offline_scan_tick()` 每 `offline_scan_minutes`
（默认 5 分钟）只列**一个**离线目录；刚提交过的目录排在最前，没有记号时按配置顺序轮询。
节奏在「离线下载 → 直链与通用目录 → 整理节奏」里改（0.8.41 起，写入
`offline_config.scan_minutes`，0 = 关闭）；`meta.offline_scan_minutes` 仍可临时压过。
直接视频为 0 时，这一轮最多再看一个子目录。也就是说最坏情况是「每 5 分钟一次读」，不会因为
离线目录里有几千个文件就变成批量列举。

`offline_add`（提交离线任务）是唯一绕过 `call()` 的接口，因为 p115client 的 proapi
端点不接受 `call()` 注入的参数；它只在你手动提交磁力/电驴时触发，一次最多 20 条。

## 2. 被限流时会发生什么

1. 识别：`state:false` 且错误文字含「频繁 / 过快 / 请求过多 / 稍后再 / too many / rate limit」，
   或 HTTP 429 / 503，判定为 `RATE_LIMITED`（普通业务拒绝如「错误的链接」不会被误判）。
2. 降速：最小间隔立刻 ×2（上限 8 倍），并进入冷却。
   **例外见 §2.1**：HTTP 405 不走这条路径。
3. 冷却：60 → 120 → 240 → 300 秒，逐次加倍；每次再乘 **±15% 抖动**（0.8.22 起）——
   否则同一时刻被限流的多个任务会以完全相同的节奏重试，冷却结束时再次同时撞上去。
   冷却期内**一个请求都不发**，直接失败返回。
4. 停批：整理任务遇到 `RATE_LIMITED` 会整批停下，任务状态 `needs_review`，
   阶段写「115 限流冷却，稍后自动重排」；不会把这批文件记成「单个文件失败」，
   也不会把移动结果误报成「结果不匹配」。
5. 恢复：冷却结束且连续成功 20 次后，间隔才回退 10%，缓慢回到基线，不做断崖式恢复。

### 2.1 WAF 封锁（HTTP 405）单独处理

405 不是 429：它是 `webapi.115.com/files` 前面的阿里云 WAF 按**时间窗**拦截，
阶梯冷却对它无效——每次重试只会把窗口往后推。实测 2026-10-30 19:55 被拦，
一直拦到 21:04 仍未解，中间 60/120/240 秒的阶梯冷却全部撞在同一堵墙上。

从 0.7.12 起：

| 项 | 行为 |
| --- | --- |
| 判定 | 仅 HTTP 405 走这条分支（429/503 仍走阶梯） |
| 封锁 | `waf_until = now + 1800s`，30 分钟内**任何请求都不发**，含播放取链 |
| 间隔 | 不抬高 `throttle_scale`——抬高也拦不住时间窗，只会让人误以为在起作用 |
| 提示 | 任务消息写明「已停止请求 30 分钟；重试会延长封锁」 |
| 解除 | 等时间窗自然过去。0.8.22 起封锁与冷却都写进 `meta.cloud_runtime`：**重启后仍在封锁期内继续封锁**，不会因为重启就把 30 分钟白送掉 |

为什么连播放也停：播放器（尤其 Emby 扫描与 Infuse 重连）会反复请求 `/play`，
每次都是一次真实取链。封锁期放行播放，等于用播放流量给封锁续期。

## 3. 依据（外部资料）

115 没有公开的频率文档，以下是能查到的公开材料与实测反馈，取其中最保守的一组做默认值：

| 来源 | 关键结论 |
| --- | --- |
| 115 生活开放平台开发者协议 5.10 / 5.11 | 平台可单方面实施请求数量限制、资源管控；禁止分布式请求、代理集群、自动化脚本规避；违规可暂停服务、冻结或回收账号。 |
| 115-Station `USAGE.md`（GitHub） | 读接口默认 1 秒；遇「服务器开小差了」调到 1500–2000 ms；**写操作（重命名/移动/删除/转存/上传）固定 ≥3 秒，是风控底线，不建议调低**。 |
| MoviePilot `u115.py` | 内置 QPS 限流器：普通 API 3 次/秒、下载 1 次/秒；社区总结的阈值是 QPS>3 冷却 5–10 分钟、QPM>50 冷却 30 分钟、QPH>300 冷却 1–2 小时。 |
| OpenList 115 驱动 | `LimitRate` 默认 2 次/秒（所有 API 合计）。 |
| 115ctln（npm） | 写操作必须单线程串行，间隔 ≥3 秒，每 10–15 个操作暂停 30 秒。 |
| 115 官方社区用户反馈 | 手动在网页端快速移动文件也被限制，约 30 分钟恢复；下载并发高会出现 405 限速。 |

据此定的默认值：读 350 ms（比 1 秒激进，但读接口风控敏感度低）、写 3000 ms（对齐「底线」）、
每 15 次写暂停 30 秒（对齐「10–15 个操作暂停」）。

## 4. 可调项与应急

设置页「服务连接 → 115 请求节奏」可改四项，保存后立即生效（不用重启）：

- `read_ms`：读间隔，0–5000。想更快可以降到 200，但遇限流会先翻倍。
- `write_ms`：写间隔，0–15000。**不建议低于 3000**，降下来是拿账号换速度。
- `burst` / `pause_ms`：突发保险丝，1–200 次 / 0–600000 ms。

真被限流时的处置顺序：

1. 看「操作记录」里有没有 `115 请求被限流：间隔提升到 X 倍，冷却 Y 秒`。
2. 等冷却结束，不要连点「重试」——每次重试都会重新计时。
3. 若一天内反复触发，把 `write_ms` 提到 5000、`burst` 降到 8，并确认没有别的东西
   （CloudDrive2 / AList / 手机端）在用同一个账号高频操作。
4. 30 分钟以上不恢复，去 115 网页端确认账号状态，必要时重新扫码登录。

## 5. 还没覆盖的

- 没有跨进程的全局限速：同一个 115 账号被 CloudDrive2、AList 等同时使用，各自限各自的。
- `offline_add` 未纳入节流（见 §1）。
- 转存/分享/STRM 同步等其它任务共用同一套节流，但没有各自的「批量暂停」策略。

已覆盖（0.8.22 起）：冷却与 WAF 封锁状态持久化在 `meta.cloud_runtime`
（`throttle_scale` / `cooldown_until` / `waf_until` / `limit_streak`，用墙钟存，
启动时换算成 monotonic 截止点），所以**重启不会把还在生效的封锁清零**。
排查当前状态可以直接看指标：`strimkeep_cloud_throttle_scale`、
`strimkeep_cloud_cooldown_seconds`、`strimkeep_cloud_waf_seconds`
（见 `docs/operations/METRICS.md`）。
