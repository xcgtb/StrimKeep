# P2 追更事件补丁重塑

基线：`f7de289b574cfa9724cebb102f765e09bbaaa053`（main，最新可达正式版本 `v1.2.0`）。提取上传 P2 包中的订阅链路，在最新源码上重新合并；不是用旧版完整文件覆盖。

## 保持的行为

- 默认五分钟 Emby 入库增量，片库事实保存成功后，仅分析受影响的已启用订阅。
- 同一轮 E16/E17/E18 合并一个通知批次；下一轮 E19/E20 是另一个独立 UUID 批次，不合并到已送达事件。
- 新集、补齐、缺集使用原季集集合差集；发送成功后才确认通知状态。旧 latest_ep 播种、暂停、手动检查和静默保存订阅的既有规则不变。
- 失败的已接受批次持续保留；已送达但写回未完成的批次只恢复状态，不重新发送。确认过的季集集合只增加，不回退。
- 不修改七维治理、云端配对、删除保护、115 删除顺序、海报加载、私人配置、媒体路径或生产数据。
- 保留 main 上的删除实时进度，以及本地/分享任一仍存在时保留海报的修复。

## 重塑部分

### 发送与慢网隔离

调度器只启动一个追更发送线程；已有线程未退出时不再创建。每轮最多发送两批，15 秒预算在批次之间检查（不是单批强制截止）；Telegram 使用原有单请求超时。入库不获取发送锁，人工/校准的网络观察也移到订阅状态锁外。状态提交与批次归属仍串行，旧观察不能覆盖更新的已确认/已排队事实。

手动立即检查仍可同步发送并返回本次实际结果，遇到另一个发送任务时显示待发送而不是阻塞入库。发送前再次核实订阅暂停状态；配置读取失败时停止发送。已经发出的网络请求不能撤销。

### 队列受控与补报

新入队最多 512 个待处理批次，总队列序列化预算 8 MiB；成功历史最多保留 256 个小摘要，不再保留大段历史分集状态。旧版已存在的超限队列不截断、不丢弃，允许逐步消化，但不继续增长。

满队列或入队写入失败时，不确认本轮新增季集，Web/日志显示异常。独立 SQLite 补报标记记录需要重新核实；队列降到一半以下后，后台至多每五分钟启动一次受控校准，将仍可验证的未确认变化重新入队。补报不恢复旧失败轮次的精确时间分组，不能声称每个未接受批次仍保留原轮次边界；已经接受的批次边界保持不变。存储本身不可写时，补报标记也可能写入失败，需人工或周期校准恢复。

通知队列、确认状态、重试与补报标记都通过既有 SQLite 状态层保存；不引入消息中间件，不清理既有数据库。Web 展示待发送数量与补报状态时只读小摘要，不反复加载整队列。

### 过期事实校准

校准默认为六小时，配置范围 1–168 小时。只展开已启用订阅的分集集合，未订阅作品不额外构造集合。

缓存事实新鲜时复用；超过 `max(15 分钟, 两个入库监控间隔)`、时间戳缺失或明显在未来时，仅用已知 Emby Series ID，或精确 TMDB 筛选重新核实。最多 64 个副本、每副本最多 5000 个分集返回，并验证身份与完整返回。不会回退全 Series 查询或扫描磁盘；超限、截断、身份不符或查询失败时保留旧状态并报错。需要 Emby 正确提供 Series 类型和 TMDB ProviderId；无法验证的作品仍可手动按原流程检查。

## 验证边界

补丁附带原 P2 回归以及重塑专项：发送中并发入库、慢 TMDB、两轮独立批次、过期精准核实、失败保留、数量/字节背压、补报代际、预算、暂停配置失败及 Web 安全提示。

自动测试使用临时数据目录、模拟 Emby/TMDB/Telegram，不操作用户媒体，不证明飞牛现场性能。Docker 构建、真实 Emby ProviderId 兼容、Telegram 实际收发、进程强杀恢复需在隔离部署验收。

Telegram 不提供与本地 SQLite 原子提交的端到端事务：远端发送成功而本地 delivered 标记尚未写入即崩溃，仍可能重复一条。长通知分片中途失败也可能在重试时重复已经成功的分片，不能承诺严格 exactly-once。

## 发布与回退

先在干净基线上检查并应用补丁，运行完整测试，再提交 main 并等待 Actions 检查和镜像构建成功。不要重打 v1.2.0，不直接替换运行容器代码。补丁不包含 /data 或私人 Compose。

生产灰度前保留数据备份和旧镜像摘要。回退旧镜像前停止新容器，保留新增队列数据；旧版不会消费新队列，后续重新升级/人工核实可能恢复通知，不能把直接删队列当作回退。
