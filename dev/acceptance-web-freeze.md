# Web 登录后卡顿修复验证（2026-10-20）

基线：v1.6.2 / main，`d9ffe772141c6fe3c326abf822d27dd3cef500c5`。
这是本地未发布源码修复；没有核验用户运行中容器的镜像摘要、日志或线程栈。

## 已复现的问题

1. `state_store.prepare/save` 原先先取得文档锁再取得 `storage._LOCK`。网盘事务先取得数据库锁，期间又会读取设置，例如 `cloud/emby_library.py` 的入库核验回写与 `cloud/workflow.py` 的计划提交。与文档写入并发时，两个线程可以互相等待，无法自行恢复。
2. `/api/library/events` 的异步生成器在事件循环中直接调用同步 SQLite 文档读取。数据库等待会阻塞同一进程的登录、健康检查等请求。异步 Emby 回调与直连播放入口也存在同步存储读取。

这两个缺陷可以解释“重启后暂时能登录，随后卡顿”的症状，但没有用户 NAS 的运行证据，不能认定其全部报错都由此造成。

## 修复

- 状态文档元数据与 SQLite 使用同一把可重入锁，消除两把锁的逆序等待，保留事务、迁移标记及修订记录。
- 片库 SSE、Emby 回调鉴权/入队与直连播放设置读取使用 `asyncio.to_thread`，将同步存储访问移出 Web 事件循环。
- 未修改账号密码、Cookie 安全策略、业务数据结构、整理/删除规则或前端。

## 验证结果

- 同一份新增回归测试运行于未修改 v1.6.2：2 项均失败。其中并发读写子进程超过 8 秒仍未退出；SSE 的数据库读取阻塞事件循环。
- 修复版后端全量：`python -m pytest dev/tests -q`，1997 项通过（55.88 秒），仅依赖弃用提示。
- 实际 FastAPI 冒烟：登录、HTTPOnly Cookie、登录后运行状态、32 个只读接口、配置往返与退出通过。
- 静态检查：`python dev/tools/static_check.py` 通过。
- 前端未修改，沿用 v1.6.2 构建产物；没有声称通过真实飞牛 NAS 的长时间负载验证。

## 应用说明

修复需要重新构建镜像并重新创建容器。仅重启旧镜像、上传源码到 Git 目录或修改登录密码不会包含本修复。
后续按新标签发布，不能覆盖已存在的 v1.6.2；不要运行本包保留的历史 v1.6.2 发布脚本。

若新镜像仍出现报错，收集错误发生时的 `docker logs --tail=100 strimkeep`、`docker stats --no-stream strimkeep` 与页面原始报错，用于区分残留阻塞、磁盘/内存压力及独立接口错误。无需清空 data 或数据库。
