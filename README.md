**1.0.0 · 影视库管理与治理**

### 一句话：把 NAS 影视库里「重复的、画质差的、缺集的」片子自动找出来，确认后清理掉，给 115 网盘腾空间。

> 如果你的环境是 **Emby + CloudDrive2 挂载 115 网盘 + STRM 刮削**，
> 而且库里同时躺着「自己整理的本地库」和「转存来的分享库」两套资源——这个工具就是给你写的。

## 快速部署：一个目录、一份 YML

使用 Docker Compose v2，在飞牛或其他 Linux NAS 上创建部署目录：

```bash
mkdir -p /vol1/1000/docker/StrimKeep
cd /vol1/1000/docker/StrimKeep
```

在这个目录中创建 `docker-compose.yml`，填入以下内容。**修改登录密码和三个媒体路径**；Emby、TMDB、Telegram 等参数启动后在 Web 设置中填写。

```yaml
services:
  strimkeep:
    # 镜像版本：固定版本便于管理；改为 latest 可跟随最新发布
    image: ghcr.io/xcgtb/strimkeep:latest
    container_name: strimkeep

    # 容器异常退出或 NAS 重启后自动启动，手动停止后不自动启动
    restart: unless-stopped

    # 使用宿主机网络，无需配置 ports
    # 默认访问地址：http://你的NAS_IP:8321
    network_mode: host

    environment:
      # 时区，影响日志时间和定时任务
      TZ: Asia/Shanghai

      # Web 登录账号和密码，部署前请修改
      # Emby、TMDB、Telegram、CD2 等连接参数在 Web 设置中填写
      WEB_USER: admin
      WEB_PASSWORD: zzx1231230

      # CD2 挂载等待开关：
      # "1"：启动时等待 CloudDrive2 挂载就绪
      # "0"：跳过启动等待
      # 此项不是 115 联动删除开关
      ENABLE_CD2_WATCHDOG: "1"

    volumes:
      # 持久化数据：配置、订阅、缓存、日志和计划存档
      # ./data 表示当前 YML 所在目录下的 data 文件夹
      # 首次启动自动创建，更新容器时保留此目录
      - ./data:/data

      # 以下三个宿主机路径是飞牛示例，请按实际目录修改
      # 只修改冒号左边；右边的容器路径和挂载参数保持不变

      # 本地 STRM 库：挂载 STRM 根目录，不是视频源目录
      # 清理本地库时，删除 NAS STRM、附属文件，
      # 并联动清理对应的 115 源文件和附属文件
      - /vol1/1000/TgtoDrive/strm/115网盘/影视媒体库:/media/local:rw

      # 分享 STRM 库：挂载分享库的 STRM 根目录
      # 清理分享库只删除 NAS STRM 和附属文件，不删除远端分享源
      - /vol1/1000/TgtoDrive/strm/115网盘/分享影视库:/media/share:rw

      # CD2 源文件库：挂载 CloudDrive2 中对应本地 STRM 的 115 目录
      # 此处应能看到真实视频、字幕等源文件
      # 两者根目录下的相对层级应对应，例如：剧集/日韩剧集/剧名/Season 1
      # rslave 用于让宿主机后续的挂载变化传播到容器
      - /vol1/1000/docker/clouddrive2/CloudDrive/影视媒体库:/media/cloud:rslave

    logging:
      # Docker 控制台日志轮转，避免日志文件持续增长
      # 此限制不影响应用内 SQLite 日志的保留策略
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

    healthcheck:
      # 定期检测应用健康状态
      # unhealthy 仅标记异常，不会单独触发 Docker 自动重启
      test: ["CMD", "python", "/app/scripts/healthcheck.py"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 20s
```

保存后，在这个目录中启动：

```bash
docker compose up -d
```

访问 **`http://NAS_IP:8321`**，使用 `admin` 和你设置的密码登录。首次启动自动创建 `data/`，以后这个目录保存配置、订阅、缓存、日志和计划存档。

本地库和分享库挂 STRM 根目录，CD2 挂对应本地库的 115 源目录。三个容器内路径保持不变；本地库清理联动 115，分享库只清理 NAS。

[下载完整 YML](docker-compose.yml) · [部署、迁移与反代说明](docs/DEPLOYMENT.md)

> 首次发布须等 GitHub 的 `v1.0.0` 镜像发布流程成功、GHCR 包设为公开后，才能拉取此版本。日常部署只需上述 YML，不需要下载源码。

## 你是否有这些困扰？

| 困扰 | StrimKeep 的做法 |
|---|---|
| 同一部电影存了两份，一份在本地库（占 115 空间）、一份在分享库，不知道该留哪份 | 自动逐片比画质，按你的策略保留更优的那份 |
| 分享库那版画质更好，可本地那份还在白占网盘空间 | 确认后删本地 STRM，并**联动删除 115 上的对应源文件** |
| 某季剧集缺了 E01，或中间被和谐断了几集，留在库里碍眼 | 自动识别「残次品」，本地 / 分享各自独立判定，谁不完整删谁 |
| 删除 STRM 后还有字幕、JSON 或空目录 | 删除时连同附属文件清理；历史残留可在「目录清理」预览并处理 |
| 追的新剧还没入完，就被当成「缺集 / 落后」误判处理 | 入库静默期：15 分钟内变动过的标题自动跳过，不入治理队列 |
| 想知道某部剧 TMDB 上更新了没、自己缺哪几集 | 追更订阅 + 缺集检查，结果可推送到 Telegram |
| 懒得开电脑，想用手机看一眼状态、顺手执行一次治理 | Telegram Bot 远程查看与执行（受保护） |

## 它是怎么工作的（30 秒看懂）

1. **扫描** —— 同时遍历「本地库」和「分享库」两个 STRM 目录，按 TMDB ID / 标题把同一部影视配对。
2. **决策** —— 比画质、比完整度，按你选的策略算出每一部该留哪份、删哪份。
3. **出清单** —— 生成一份「治理计划」，逐条写明**删什么、为什么删**。⚠️ **这一步不动任何文件。**
4. **执行** —— 你看完清单、点击确认，它才真正删除。

> ### ⚠️ 安全第一（请务必读完）
>
> **默认流程永远是：先扫描 → 再生成计划 → 最后由你手动确认执行。工具不会自动删除任何东西。**
>
> 即使开启了「定时巡检」，也**只扫描并推送通知，不会自动清理**。
>
> **删除是不可逆的**：STRM 与云端源文件都是直接删除，工具不保留副本、不提供回收站。
>
> 因此**强烈建议第一次部署只做预览**，确认清单符合预期后，再执行清理。

## 一个例子

以《某某剧》第二季为例，两库都有：

**情况 A —— 分享库画质更好、且完整**

- 本地库：1080P，E01–E10 完整
- 分享库：2160P HDR，E01–E10 完整

→ 清单显示「《某某剧》S02：分享画质达标 10/10 集 → 删本地腾网盘」
→ 本地那份被删除（并联动删掉 115 源文件），Emby 里继续正常播放分享库那份。

**情况 B —— 分享库画质好但缺集**

- 本地库：1080P，E01–E10 完整
- 分享库：2160P，**缺 E05**（中间断层，疑似被和谐）

→ 分享库那份判定为「残次品」被清理，本地 1080P 完整版保留。
→ **宁要完整，不要残缺**：不会因为画质更高就留下缺集的版本。

## 核心功能

- **双库治理**：对比本地库与分享库的电影 / 剧集，按画质与完整度生成治理计划。
- **逐集择优**：剧集逐集对齐后按达标率择优，分享画质更优则删本地（联动删 115 源文件腾空间），本地更优则淘汰分享。
- **残次品清理**：前序缺失（缺 E01）、中间断层（疑似被和谐）的不完整季，本地与分享**各自独立判定**——谁不完整删谁，完整的那份正常进入画质对比。
- **库内多版本去重**：同一库内同一片 / 同一集存在多份 STRM（洗版、追更残留）时，只保留画质最优的一份，低版本联动删除腾空间。
- **多季保护**（关闭 / 开启）：「开启」档：两边季集合相同则整体比画质留优者；一边季更多则保护那份合集（不被对方掏空）；部分重叠两边同季都不动。
- **配对与特别篇策略**：两库配对可选「剧名 + 年份」或「TMDB 优先」；特别篇（S00）可选画质对比 / 忽略 / 清理。
- **目录清理**：扫描选定范围内的空媒体目录或仅含已知附属文件的媒体目录；可选整个媒体库、本地库、分享库及指定目录。预览后执行，结果弹窗并写入计划存档。
- **入库进度**：影视探索 / 片库映射展示「已完整 / 连载中 X/Y / 未入库」及双库分库进度。
- **白名单 / 豁免**：按关键词跳过治理。
- **TMDB / Emby**：缺集、缺季检查与媒体库状态。
- **Telegram Bot**：远程查看状态并执行受保护的治理操作。
- **二次确认**：治理计划与实际删除分离。
- **CloudDrive2 联动**：本地库清理通过 CD2 对应 115 源目录执行；分享库只清理 NAS。CD2 看门狗仅检查挂载就绪，不是删除开关。

## 治理逻辑

### 画质对比规则（7 维，可自定义）

两库版本比画质的**唯一依据**，没有任何隐藏打分。在「规则设置 → 治理规则 → 画质对比规则」里调整：

- 从上到下**逐项比较**：某一项两边档位不同，排在前面的档位胜出，后面的项不再比较；两边相同（或都识别不出）才看下一项；全部打平，交给「平局保留本地」开关。
- 每一项可**启用 / 关闭**（关闭只是跳过，不会反向优先）、可**上下移动**调整优先级、可**重排档位顺序**；无法识别的规格永远排在该项最后，不会被强行判为更优。
- 识别全部基于**文件名**（STRM 取不到云端真实文件大小，所以没有「文件大小」这一项）。

| 默认顺序 | 维度 | 说明 |
|---|---|---|
| 1 | 发布组 | 按你维护的发布组列表比较（取自文件名末尾「-组名」）；**默认关闭**，列表为空时不参与 |
| 2 | 资源类型 | UHD Remux > Remux > UHD BluRay > BluRay > WEB-DL > WEBRip > HDTV > DVD |
| 3 | 分辨率 | 8K > 4K > 2K > 1080p > 720p > SD |
| 4 | 动态范围 | Dolby Vision（P7 > P5 > P8 > 未识别）> HDR10+ > HDR Vivid > HDR10 > HDR / HLG > SDR |
| 5 | 色深 | 12bit > 10bit > 8bit |
| 6 | 音频规格 | TrueHD Atmos / DTS:X > TrueHD / DTS-HD MA > LPCM / FLAC > Audio Vivid > DD+ Atmos > DD+ > DTS > AC3 > AAC |
| 7 | 帧率 | 60 > 50 > 30 > 25 > 24 fps（59.94 / 29.97 / 23.976 分别归入 60 / 30 / 24 档） |

> 注意：默认顺序下**资源类型排在分辨率之前**，所以 1080p BluRay 会被认为优于 4K WEB-DL。如果你更看重分辨率，把「分辨率」上移到第一位即可。

**关键策略，保存要二次确认**：规则保存后立即生效（配置热加载），直接决定「删本地还是删分享」，所以编辑只是草稿——页面会提示「有未保存的改动」，点「保存规则」会弹窗列出本次改动明细，等几秒后才能确认；「恢复默认」同样要确认；有未保存改动时切换页签或刷新页面会被拦截。规则指纹改变后旧治理计划不可执行，需要重新扫描。

**对比测试**：规则设置里填入两个文件名，可按当前已保存的规则逐项看谁胜、在哪一项决出胜负；治理清单的每条动作详情里也有同样的逐维对比表。

### 决策模型（规则设置中切换）

| 策略 | 行为 |
|---|---|
| 画质优先（默认） | 两库比画质，高者胜出；平局按「平局保留本地」开关决定 |
| 保留本地 | 本地库永远优先，分享库只作补充 |
| 保留分享 | 分享库永远优先，节省 115 网盘空间 |

### 双库配对策略（规则设置中切换）

两库里的同一部片子怎么认定为「同一部」，决定了谁和谁去比画质：

| 策略 | 行为 |
|---|---|
| 剧名 + 年份（默认） | 按剧名和年份配对。**更安全**，即使 TMDB 标识写错也不会误配 |
| TMDB 优先 | 优先按 TMDB ID 配对，**召回更高**；标识冲突时回退到剧名配对 |

> 切换配对策略后，已生成的旧治理计划会失效，需要重新扫描。同一个 TMDB 标识对应多个不同标题时，只在治理页提示「标识冲突」，**不会进入自动清理**。

### 特别篇（S00）策略（规则设置中切换）

Emby 里的 S00 / Specials 单独处理，三种方式：

| 策略 | 行为 |
|---|---|
| 画质对比（默认） | 特别篇同样比画质，平局遵循「平局保留本地」设置 |
| 忽略 | S00 不参与治理，不会出现在清单里 |
| 清理 | 本地与分享库中的特别篇全部删除 |

> 「清理」会直接删除两库里的特别篇，不可恢复，请先确认扫描清单再执行。

### 剧集治理（按季原子处理）

- **残次品独立判定**：本地、分享各自独立看「是否从 E01 起连续无断层」——前序缺失（缺 E01）或中间断层（疑似被和谐）的那一份判定为残次品删除，不做双库合并对照；完整的那一份正常进入画质对比。
- **逐集达标率择优**：两边都完整且集数对齐后，逐集比画质。**当分享画质达标的集数占比达到配置阈值（默认 90%，可设 50%–100%），且分享总集数不少于本地时**，删除本地、保留分享；否则淘汰分享、保留本地（单季只作用于单一库，不做跨库拆分）。
- **多季保护两档**：
  - 关闭：逐季独立择优。
  - 开启（默认）：**画质对比照常进行，多季保护只负责不让任何一边被掏空**，按「季集合的覆盖关系」判定：
    - **两边季集合完全相同**（如两边都是 S01–S18）：单库 vs 单库整体比画质、留优者——分享逐季逐集全部达标则整体删本地，否则整体淘汰分享。
    - **一边季更多**（另一边的季是它的子季）：保护季多的那份合集，子季一方的同季副本淘汰、不比画质。分享是合集则淘汰本地同季副本，本地是合集则淘汰分享同季副本。
    - **双方各有对方没有的季**（部分重叠）：删哪边都会让该库断层，同季两边都不动，只处理各自的残次品。
    - **S00（特别篇）算作一季**参与上述判断：特别篇策略为「画质对比」时，S00 不再单独比画质，而是跟随该剧多季保护的结果（保护谁，对方的 S00 一并淘汰），避免分享（或本地）的 S00 画质更好就把对方合集掏空；策略为「忽略 / 清理」时不变。
    - **单季剧**不进入多季保护，仍按逐集完整性 / 画质对比。
    - 保护分享时，若分享某季集数达不到本地，按原有规则淘汰这一季的分享（本地更全）。

### 入库静默期

剧集 / 电影刚入库时常常只入了一部分。某个标题（含双库、所有季）的任一目录在 **15 分钟内**有新增或变动，就暂不进入治理队列（静默跳过，不出现在清单里），过了静默期再自然纳入；执行清理前的二次校验同样遵守。可在规则设置里调整入库静默时间，`0` 表示关闭；设置只保存在 SQLite 中。

### 删除的安全机制

工具做了多层防误删，这也是它敢自动删文件的底气：

- **删除分级**：只有云端源文件被**精确匹配**（文件名完全一致，或标准化后唯一匹配）时才允许自动删除；出现多个候选、只能靠目录唯一兜底匹配、或根本找不到时，**一律保留 STRM 不动**。
- **删不动就不删**：云端源文件删除失败或超时，对应的 STRM 也会保留，绝不留下"指针还在、源没了"的坏记录。
- **附属文件连根拔**：删除 STRM 时，同名的 `-mediainfo.json`、`.nfo`、`.srt`、`.ass` 等附属文件一并清理，且**只匹配同名文件**，不会误伤同目录下其他集的字幕。
- **目录白名单**：库根目录、分类目录永不被自动删除；只有媒体专属目录参与清理。

## Web 界面

同一套页面自适应手机与电脑，支持浅色 / 深色主题。侧栏按「媒体库 / 治理与追更 / 运行与设置」分为三组，共 10 个直接入口；电脑端常驻，手机端通过左上角菜单或底部「更多」展开。运行状态区域显示服务连接、Emby/TMDB 最近状态、机器人、当前任务、数据保存状态和更新时间。双库治理、入库与晨报、日志中心与存档保留顶部子页切换。刷新浏览器后会停留在当前页面。

|---|---|

## 常见问题

**会误删我的文件吗？**
多层防护：只有精确匹配到云端源文件才会自动删；匹配存疑（多个候选 / 仅目录兜底 / 找不到）一律保留；云端删除失败则 STRM 也不删。删除前还有一次基于入库静默期的二次校验。治理清理结果写入计划存档，日常运行过程在日志中心查看。

**删掉的文件还能找回吗？**

**不能。所有删除都是立即且不可逆的——工具不保留副本、不提供回收站。**

- **STRM 文件**：直接删除。
- **云端 115 源文件**：同样直接删除，删掉的是网盘上的真实文件。
- **同名附属文件**：字幕 / nfo / mediainfo 一并删除。

所以**第一次部署务必只做预览**：先扫描出清单、不要点执行，确认清单完全符合预期后再正式清理。

**必须使用 115 网盘和 CloudDrive2 吗？**
不必须。双库扫描和分享库清理不依赖 CD2。本地库联动清理依赖 CD2 挂载的对应 115 源目录；源文件匹配或删除失败时会跳过并说明原因。

**支持 Jellyfin / Plex 吗？**
目前媒体库状态、缺集检查是通过 **Emby API** 实现的。Jellyfin 的 API 与 Emby 高度相似，但未经官方验证；Plex 暂不支持。如果你只想要双库治理，不填 Emby 也能用。

**忘记 Web 密码了怎么办？**
修改 `docker-compose.yml` 里的 `WEB_PASSWORD`，然后 `docker compose up -d` 重启容器即可。登录会话 Cookie 有效期为 30 天。

> **反向代理访问：** 登录后的写操作带有 CSRF 同源校验（Origin 必须与访问的 Host 一致）。若你用域名反代、且代理没有透传 `Host` / `X-Forwarded-Host`，操作会返回 403，此时在环境变量里设置 `ALLOWED_ORIGINS=https://你的域名` 即可；直连 `IP:端口` 无需配置。

**8321 端口被占用了？**
容器默认监听 8321（`network_mode: host`）。可在 `docker-compose.yml` 中覆盖 `command` 修改 uvicorn 端口，并同步设置 `PORT` 环境变量（供容器健康检查使用）。

**治理计划保留多久？**
未执行的旧计划保留 **7 天**；已执行计划与治理清理结果长期保存，供事后回查。配置、订阅状态、缓存、计划、日志统一写入 `/data/state/strimkeep.db`，不再双写 JSON/JSONL，也不产生滚动副本。运行日志约保留最近 10,000 行，清理存档不受此上限影响。旧 JSON/JSONL 只在首次迁移时读取，成功标记后不再覆盖新状态；原文件暂留，但不继续增长。

项目名为 **StrimKeep**，Compose 服务和容器名为 `strimkeep`，SQLite 数据文件为 `/data/state/strimkeep.db`。从旧项目迁移时请先按 [部署说明](docs/DEPLOYMENT.md) 处理数据库文件名，不能直接覆盖旧部署后启动。
