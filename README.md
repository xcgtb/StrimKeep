# 🎬 StrimKeep

**StrimKeep｜面向 STRM 双库的影视管理与治理工具**

![License: MIT](https://img.shields.io/badge/License-MIT-blueviolet?style=for-the-badge)
![Python 3.11](https://img.shields.io/badge/Python-3.11-blue?style=for-the-badge)
![Docker Ready](https://img.shields.io/badge/Docker-Ready-blue?style=for-the-badge)

> **一套面板，管理两套 STRM 影视库。** 对比本地库与分享库的画质和完整性，找出重复版本、残缺剧集与缺集情况；先生成治理计划，确认后再执行清理。

StrimKeep 主要面向使用 **飞牛 OS / Linux NAS + STRM + Emby** 的用户，特别适合同时维护「本地 STRM 库」和「分享 STRM 库」，并通过 **CloudDrive2 挂载 115 网盘** 管理本地源文件的场景。除了双库治理，还提供影视探索、片库映射、追更订阅、入库汇报与 Telegram 通知。

**重要：** 本工具具有真实文件删除能力。主动执行清理时，除 NAS 上的 STRM 文件外，**本地库还可能联动删除 115 网盘中的真实源文件**。删除操作不可撤销，首次使用请务必先预览，不要直接执行。

## 快速部署

### 1. 准备目录

确保 NAS 已安装 Docker 和 **Docker Compose v2**。以飞牛 OS 为例，通过 SSH 执行：

```bash
mkdir -p /vol1/1000/docker/StrimKeep
cd /vol1/1000/docker/StrimKeep
```

### 2. 创建 `docker-compose.yml`

将仓库中的 [`docker-compose.yml`](docker-compose.yml) 放入上述目录，然后根据实际环境修改：

1. **`WEB_PASSWORD`**：设置高强度登录密码，不能保留示例占位值。
2. **三个 `volumes` 宿主机路径**：分别指向本地 STRM 库、分享 STRM 库、CloudDrive2 对应的真实源文件库。
3. **`ENABLE_CD2_WATCHDOG`**：`"1"` 表示启动时等待 CD2 挂载就绪；如果不需要等待可改为 `"0"`。它**不是云端删除功能的开关**。

**GitHub 模板默认镜像：`ghcr.io/xcgtb/strimkeep:latest`。** `latest` 是发布方维护的滚动标签，不代表启动时自动检查新版本；后续升级仍需手动 `docker compose pull`。如果需要固定版本以便回滚，请将标签改为具体已发布的版本号。

下面是精简示例；可直接使用仓库提供的完整 YML（含中文注释与飞牛路径示例）：

```yaml
services:
  strimkeep:
    image: ghcr.io/xcgtb/strimkeep:latest
    container_name: strimkeep
    restart: unless-stopped
    network_mode: host
    environment:
      TZ: Asia/Shanghai
      WEB_USER: "admin"
      WEB_PASSWORD: "CHANGE_ME_TO_A_STRONG_PASSWORD"
      ENABLE_CD2_WATCHDOG: "1"
    volumes:
      - ./data:/data
      - /你的本地STRM库:/media/local:rw
      - /你的分享STRM库:/media/share:rw
      - /你的CloudDrive2源文件库:/media/cloud:rslave
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
    healthcheck:
      test: ["CMD", "python", "/app/scripts/healthcheck.py"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 20s
```

> **路径一定要分清：** `/media/local` 和 `/media/share` 对应 NAS 上的 **STRM 根目录**；`/media/cloud` 对应 CD2 中**本地 STRM 库的 115 实际源文件目录**。只改挂载冒号左边的路径，不改右边的容器路径或挂载模式。请确保宿主机目录已存在。
>
> **密码提示：** 若在 Compose 文件里直接设置含 `$` 的密码，须将每个 `$` 写成 `$$`，以避免 Docker Compose 将其解析为变量。

### 3. 检查并启动

在 `docker-compose.yml` 所在目录执行：

```bash
# 检查 Compose 语法
docker compose config -q

# 拉取最新发布镜像并启动
docker compose pull
docker compose up -d

# 查看运行状态
docker compose ps
```

浏览器访问 **`http://你的NAS_IP:8321`**，使用配置好的 Web 账号和密码登录。

首次启动会在当前目录下创建 `data/`，用于保存配置、订阅、SQLite 数据库、缓存、日志和治理计划。**升级或重建容器时必须保留 `data/`；不要随意删除数据目录或执行数据卷清理命令。**

如果镜像无法拉取，请先核对 [GitHub Releases](https://github.com/xcgtb/StrimKeep/releases) 与 GHCR 镜像公开状态，以及发布流程是否推送了 `latest` 标签。无需克隆源码或自行构建即可使用发布镜像。

更多路径示例、迁移、反向代理与排错：**[完整部署教程](docs/DEPLOYMENT.md)**。

## 首次使用

建议按以下顺序完成一次**不删除任何文件**的测试：

1. 登录 Web，在「规则设置 → 服务连接」填写并测试 Emby、TMDB 等服务参数；不需要的功能可以暂不配置。
   没有透明代理时，可在同页开启「外部服务 HTTP 代理」，填写例如 `http://192.168.1.2:7890`，按需填用户名、密码，测试后保存。TMDB 查询、海报和 Telegram 使用此代理，Emby 不受影响；配置保留在数据目录，更新镜像后不丢失。
2. 检查本地库、分享库及 CloudDrive2 映射范围是否正确，尤其确认本地 STRM 与 115 源文件的目录层级对应。
3. 进入「双库治理」，先扫描并查看治理清单，核对配对结果、画质判定、待清理路径与原因。
4. 对于新入库、正在追更或匹配结果不确定的内容，先保持不处理；可调整静默期、规则或白名单后重新扫描。
5. 确认清单完全符合预期后，再主动执行清理。**切勿把预览按钮和执行按钮混为一谈。**

**工作流程：** 扫描双库 → 按规则计算决策 → 生成可预览清单 → 用户主动确认 → 执行并归档结果。定时巡检只扫描和通知，不会自行触发删除；但是在 Web 中点击删除，或使用受权限保护的 Telegram `/clean` 等主动执行操作，可能真正删除文件。

## 你是否有这些困扰？

| 困扰 | StrimKeep 的做法 |
|---|---|
| 同一部电影存了两份，一份在本地库（占 115 空间）、一份在分享库，不知道该留哪份 | 按当前规则对比画质，生成建议保留与清理的版本清单 |
| 分享库那版画质更好，可本地那份还在白占网盘空间 | 确认后删本地 STRM，并**联动删除 115 上的对应源文件** |
| 某季剧集缺了 E01，或中间被和谐断了几集，留在库里碍眼 | 识别前序缺集或中间断层，双库分别判断并列入待确认清单 |
| 删除 STRM 后还有字幕、JSON 或空目录 | 删除时连同附属文件清理；历史残留可在「目录清理」预览并处理 |
| 追的新剧还没入完，就被当成「缺集 / 落后」误判处理 | 默认 15 分钟入库静默期：近期变动的标题暂不进入治理队列 |
| 想知道某部剧 TMDB 上更新了没、自己缺哪几集 | 追更订阅 + 缺集检查，结果可推送到 Telegram |
| 懒得开电脑，想用手机看一眼状态、顺手执行一次治理 | Telegram Bot 远程查看与执行（受保护） |

## 治理流程：先预览，再执行

1. **扫描** —— 同时遍历「本地库」和「分享库」两个 STRM 目录，按 TMDB ID / 标题把同一部影视配对。
2. **决策** —— 比画质、比完整度，按你选的策略算出每一部该留哪份、删哪份。
3. **出清单** —— 生成一份「治理计划」，逐条写明**删什么、为什么删**。⚠️ **这一步不动任何文件。**
4. **执行** —— 你看完清单、点击确认，它才真正删除。

> ### ⚠️ 安全提示（请务必阅读）
>
> **常规治理流程是：先扫描 → 生成计划 → 主动确认后执行。定时巡检不会自动执行删除，但 Web 删除操作与获得授权的 Telegram 清理命令会真正执行删除。**
>
> 即使开启了「定时巡检」，也**只扫描并推送通知，不会自动清理**。
>
> **删除是不可逆的**：STRM 与云端源文件都是直接删除，工具不保留副本、不提供回收站。
>
> 因此**第一次部署请只做预览**，确认清单符合预期后，再执行清理。

## 两个治理示例

以《某某剧》第二季为例，两库都有：

**情况 A —— 分享库画质更好、且完整**

- 本地库：1080P，E01–E10 完整
- 分享库：2160P HDR，E01–E10 完整

→ 清单显示「《某某剧》S02：分享画质达标 10/10 集 → 删本地腾网盘」
→ 如果用户确认执行，且 115 源文件精确匹配并成功删除，本地 STRM 及其附属文件才会继续清理；分享库版本仍予保留。

**情况 B —— 分享库画质好但缺集**

- 本地库：1080P，E01–E10 完整
- 分享库：2160P，**缺 E05**（中间断层，疑似被和谐）

→ 分享库会被识别为残缺版本并进入待清理清单；确认执行后清理该分享版本，保留本地 1080P 完整版。
→ **宁要完整，不要残缺**：不会因为画质更高就留下缺集的版本。

## 核心功能

- **双库治理**：对比本地库与分享库的电影 / 剧集，按画质与完整度生成治理计划。
- **逐集择优**：剧集逐集对齐后按达标率择优，分享画质更优则删本地（联动删 115 源文件腾空间），本地更优则淘汰分享。
- **残缺剧集识别**：前序缺失（缺 E01）、中间断层（疑似被和谐）的不完整季，本地与分享**各自独立判定**——谁不完整删谁，完整的那份正常进入画质对比。
- **库内多版本去重**：同一库内同一片 / 同一集存在多份 STRM（洗版、追更残留）时，只保留画质最优的一份，低版本联动删除腾空间。
- **多季保护**（关闭 / 开启）：「开启」档：两边季集合相同则整体比画质留优者；一边季更多则保护那份合集（不被对方掏空）；部分重叠两边同季都不动。特别篇策略为「画质对比」时，**S00 算作一季**参与季集合判断。
- **配对与特别篇策略**：两库配对可选「剧名 + 年份」或「TMDB 优先」；特别篇（S00）可选画质对比 / 忽略 / 清理。
- **目录清理**：扫描选定范围内的空媒体目录或仅含已知附属文件的媒体目录；可选整个媒体库、本地库、分享库及指定目录。预览后执行，结果弹窗并写入计划存档。
- **入库进度**：影视探索 / 片库映射展示「已完整 / 连载中 X/Y / 未入库」及双库分库进度。
- **白名单 / 豁免**：按关键词跳过治理。
- **TMDB / Emby**：缺集、缺季检查与媒体库状态。
- **Telegram Bot**：远程查看状态并执行受保护的治理操作。
- **执行确认**：扫描计划与真实文件删除分离；目录清理、详情页删除同样应确认操作范围。
- **CloudDrive2 联动**：本地库清理通过 CD2 对应 115 源目录执行；分享库只清理 NAS。CD2 看门狗仅检查挂载就绪，不是删除开关。

## 治理逻辑

### 画质对比规则（7 维，可自定义）

两库版本比画质的**唯一依据**，没有任何隐藏打分。在「规则设置 → 治理规则 → 画质对比规则」里调整：

- 从上到下**逐项比较**：某一项两边档位不同，排在前面的档位胜出，后面的项不再比较；两边相同（或都识别不出）才看下一项；全部打平，交给「平局保留本地」开关。
- 每一项可**启用 / 关闭**（关闭只是跳过，不会反向优先）、可**上下移动**调整优先级、可**重排档位顺序**；无法识别的规格永远排在该项最后，不会被强行判为更优。
- 识别全部基于**文件名**（STRM 取不到云端真实文件大小，所以没有「文件大小」这一项）。

| 默认顺序 | 维度 | 说明 |
|---|---|---|
| 1 | 发布组 | 按你维护的发布组列表比较（取自文件名末尾「-组名」）；**默认关闭**，列表为空时不参与 |
| 2 | 资源类型 | **默认关闭，可自行启用**；UHD Remux > Remux > UHD BluRay > BluRay > WEB-DL > WEBRip > HDTV > DVD |
| 3 | 分辨率 | 8K > 4K > 2K > 1080p > 720p > SD |
| 4 | 动态范围 | Dolby Vision（P7 > P5 > P8 > 未识别）> HDR10+ > HDR Vivid > HDR10 > HDR / HLG > SDR |
| 5 | 帧率 | 60 > 50 > 30 > 25 > 24 fps（59.94 / 29.97 / 23.976 分别归入 60 / 30 / 24 档） |
| 6 | 色深 | 12bit > 10bit > 8bit |
| 7 | 音频规格 | TrueHD Atmos / DTS:X > TrueHD / DTS-HD MA > LPCM / FLAC > Audio Vivid > DD+ Atmos > DD+ > DTS > AC3 > AAC |

默认发布组、资源类型关闭，其余五项开启，先比较分辨率。例如 4K WEB-DL 默认优于 1080p BluRay；如果启用资源类型并保持它在分辨率之前，则先按资源类型决定。升级保留用户已保存的规则；新配置及「恢复默认」使用上表的顺序与开关。

**关键策略，保存要二次确认**：规则保存后立即生效（配置热加载），直接决定「删本地还是删分享」，所以编辑只是草稿——页面会提示「有未保存的改动」，点「保存规则」会弹窗列出本次改动明细，等几秒后才能确认；「恢复默认」同样要确认；有未保存改动时切换页签或刷新页面会被拦截。规则指纹改变后旧治理计划不可执行，需要重新扫描。

**对比测试**：规则设置里填入两个文件名，可按当前已保存的规则逐项看谁胜、在哪一项决出胜负；治理清单的每条动作详情里也有同样的逐维对比表。

### 决策模型（规则设置中切换）

| 策略 | 行为 |
|---|---|
| 画质优先（默认） | 两库比画质，高者胜出；平局按「平局保留本地」开关决定 |
| 保留本地 | 本地库永远优先，分享库只作补充 |
| 保留分享 | 分享库永远优先，节省 115 网盘空间 |

### 双库配对策略（规则设置中切换）

两库里的同一部片子怎么认定为「同一部」，决定了谁和谁去比画质：

| 策略 | 行为 |
|---|---|
| 剧名 + 年份（默认） | 按剧名和年份配对。**更安全**，即使 TMDB 标识写错也不会误配 |
| TMDB 优先 | 优先按 TMDB ID 配对，**召回更高**；标识冲突时回退到剧名配对 |

> 切换配对策略后，已生成的旧治理计划会失效，需要重新扫描。同一个 TMDB 标识对应多个不同标题时，只在治理页提示「标识冲突」，**不会进入自动清理**。

### 特别篇（S00）策略（规则设置中切换）

Emby 中的 S00 / Specials 提供三种处理方式：

**画质对比（默认）**

- **开启多季保护（默认）**：S00 **算作一季**，参与本地库与分享库的季集合覆盖关系判断，跟随合集治理结果；不单独比较画质，也不单独使用「平局保留本地」决定去留。
- **关闭多季保护**：S00 作为独立季比较画质；只有画质打平时，才按「平局保留本地」设置决定。

**忽略**：S00 不参与治理，不出现在治理清单中。

**清理**：两库中的 S00 均列入待清理计划，手动确认执行后删除。

**示例**：本地库有 S01、S02；分享库有 S00、S01、S02。选择「画质对比」且开启多季保护时，分享库因多出 S00 而属于季集合更多的一方，按多季合集保护规则处理，而不是单独对 S00 使用「平局保留本地」。

> **删除提醒**：「清理」会将两库 S00 纳入删除计划，确认执行后不可恢复。请先检查扫描清单。

### 剧集治理（按季原子处理）

**残次品独立判定**：本地库与分享库分别检查剧集是否从 E01 起连续、是否存在中间断层。前序缺失或中间断层的版本按残次品规则处理；完整版本正常进入画质对比，不把两库合并凑成完整季。

**逐集达标率择优**：两边都完整且集数对齐后，逐集比较画质。分享版画质达标的集数占比达到配置阈值（默认 90%，可设 50%–100%），且分享总集数不少于本地时，删除本地、保留分享；否则淘汰分享、保留本地。单季只作用于单一库，不做跨库拆分。

### 多季合集保护

**关闭**：各季独立按完整性和画质规则择优。

**开启（默认）**：按两库「季集合的覆盖关系」决定保护哪一方，避免合集被另一库逐季掏空。具体分为以下情况：

**情况一：两边季集合完全相同**

例如本地与分享都有 S01–S18。两库作为完整合集进行画质比较：分享逐季逐集全部达标，则整体淘汰本地；否则整体淘汰分享。

**情况二：一边季更多，另一边是其子集**

保护季数更多的合集，同季副本不再比画质。分享是合集则淘汰本地的同季副本；本地是合集则淘汰分享的同季副本。

**情况三：双方各有对方没有的季（部分重叠）**

为避免任一库出现季断层，重叠的同季副本两边都不动，仅处理各自的残次品。

**S00 如何计算**

特别篇策略为「画质对比」时，**S00 算作一季**参与以上季集合判断，跟随多季保护结果；不独立比较画质，也不单独套用「平局保留本地」。特别篇策略为「忽略」或「清理」时，分别按所选策略处理。

**其他边界规则**

- 单季剧不进入多季保护，仍按逐季完整性和画质规则处理。
- 保护分享合集时，如果分享某季集数少于本地，该季仍按原有规则淘汰分享版本，保留更完整的本地版本。

### 入库静默期

剧集 / 电影刚入库时常常只入了一部分。某个标题（含双库、所有季）的任一目录在 **15 分钟内**有新增或变动，就暂不进入治理队列（静默跳过，不出现在清单里），过了静默期再自然纳入；执行清理前的二次校验同样遵守。可在规则设置里调整入库静默时间，`0` 表示关闭；设置只保存在 SQLite 中。

### 删除的安全机制

清理过程中采用保守的源文件匹配与分级保护策略：

- **删除分级**：只有云端源文件被**精确匹配**（文件名完全一致，或标准化后唯一匹配）时才允许继续执行云端删除；出现多个候选、只能靠目录唯一兜底匹配、或根本找不到时，**一律保留 STRM 不动**。
- **删不动就不删**：云端源文件删除失败或超时，对应的 STRM 也会保留，绝不留下"指针还在、源没了"的坏记录。
- **附属文件精确清理**：删除 STRM 时，同名的 `-mediainfo.json`、`.nfo`、`.srt`、`.ass` 等附属文件一并清理，且**只匹配同名文件**，不会误伤同目录下其他集的字幕。
- **目录白名单**：库根目录、分类目录永不被自动删除；只有媒体专属目录参与清理。

## Web 界面

Web 页面适配电脑与手机，支持浅色 / 深色主题。导航按照「媒体库」「治理与追更」「运行与设置」分组；手机端可通过菜单展开。页面顶部会呈现服务连接、任务运行、数据更新时间等信息。

### 媒体库

- **媒体总览**：查看 STRM 数量、本地 / 分享占比、剧集与电影统计、Emby / TMDB 状态；提供近 24 小时入库、追更订阅、晨报、白名单入口，以及待清理、受保护、豁免和片库健康概况。分类统计可切换合计 / 本地 / 分享，并跳转到片库映射筛选。
- **片库映射**：按 Emby 媒体库查看剧集与电影，支持海报墙、搜索、状态 / 库范围筛选、「读缓存」与「重新对照」。详情页显示分季集数、TMDB 与双库对照、手动完结以及 Emby 跳转。**详情页也包含直接删除本地 / 分享库的操作**：先试算文件数、再二次确认；删除本地库可能联动清理 115 源文件。
- **影视探索**：浏览和搜索 TMDB 内容，按地区、类型、题材、年份等筛选；海报展示「已完整 / 连载中 X/Y / 未入库」等入库信息，剧集可添加追更订阅。

### 治理与追更

- **双库治理**：扫描、查看清单、逐项检查匹配与画质依据、确认执行；可按本地待清理、分享待清理、受保护、豁免筛选。新扫描会根据当前规则生成计划，支持取消扫描。
- **目录清理**：选定全库、本地库、分享库或指定目录后，预览空目录及仅含已知附属文件的媒体目录；确认后执行并记录清理结果。分享库只清理 NAS，本地库可按规则联动 CD2。
- **追更订阅**：管理订阅的启用、暂停、删除与「立即检查」；可设置 TMDB 缺集对照、后台轮询与检查间隔。
- **入库与晨报**：查看近 24 小时新增影片与剧集，支持读缓存和立即扫描；晨报可配置内容、发送时间、提前预扫、预览与 Telegram 推送。

### 运行与设置

- **日志中心**：查看治理、订阅、入库与机器人运行日志，可暂停、刷新、下载；页面最多展示 500 行，切离时暂停实时轮询。
- **计划存档**：回看治理计划、清理结果及失败原因。待执行计划超过 2 小时不可执行；未执行的旧计划保留 7 天，已执行及清理结果长期保存。
- **规则设置**：配置治理策略、七维画质优先级、配对、多季保护、特别篇、白名单、静默期和定时任务；填写 Emby、TMDB、Telegram 等服务参数并测试连接。**修改治理规则会影响后续删除决策，规则变更后应重新扫描。**

## 常见问题

**有哪些防误删措施？**
多层防护：本地库必须精确匹配到云端源文件才允许继续删除；匹配存疑（多个候选 / 仅目录兜底 / 找不到）一律保留；云端删除失败则 STRM 也不删。删除前还有一次基于入库静默期的二次校验。治理清理结果写入计划存档，日常运行过程在日志中心查看。

**删掉的文件还能找回吗？**

**本工具不提供撤销操作、回收站或备份恢复功能；不要依赖删除后可找回。**

- **STRM 文件**：直接删除。
- **云端 115 源文件**：同样直接删除，删掉的是网盘上的真实文件。
- **同名附属文件**：字幕 / nfo / mediainfo 一并删除。

所以**第一次部署务必只做预览**：先扫描出清单、不要点执行，确认清单完全符合预期后再正式清理。

**必须使用 115 网盘和 CloudDrive2 吗？**
不必须。双库扫描和分享库清理不依赖 CD2。本地库联动清理依赖 CD2 挂载的对应 115 源目录；源文件匹配或删除失败时会跳过并说明原因。

**支持 Jellyfin / Plex 吗？**
目前媒体库状态、缺集检查是通过 **Emby API** 实现的。Jellyfin 的 API 与 Emby 高度相似，但未经官方验证；Plex 暂不支持。如果你只想要双库治理，不填 Emby 也能用。

**忘记 Web 密码了怎么办？**
修改 `docker-compose.yml` 里的 `WEB_PASSWORD`，然后在部署目录执行 `docker compose up -d` 使环境变量生效。登录会话 Cookie 有效期为 30 天。

> **反向代理访问：** 登录后的写操作带有 CSRF 同源校验（Origin 必须与访问的 Host 一致）。若你用域名反代、且代理没有透传 `Host` / `X-Forwarded-Host`，操作会返回 403，此时在环境变量里设置 `ALLOWED_ORIGINS=https://你的域名` 即可；直连 `IP:端口` 无需配置。

**8321 端口被占用了？**
容器默认监听 8321（`network_mode: host`）。可在 `docker-compose.yml` 中覆盖 `command` 修改 uvicorn 端口，并同步设置 `PORT` 环境变量（供容器健康检查使用）。

**治理计划保留多久？**
未执行的旧计划保留 **7 天**；已执行计划与治理清理结果长期保存，供事后回查。配置、订阅状态、缓存、计划、日志统一写入 `/data/state/strimkeep.db`，不再双写 JSON/JSONL，也不产生滚动副本。运行日志约保留最近 10,000 行，清理存档不受此上限影响。旧 JSON/JSONL 只在首次迁移时读取，成功标记后不再覆盖新状态；原文件暂留，但不继续增长。

项目名为 **StrimKeep**，Compose 服务和容器名为 `strimkeep`，SQLite 数据文件为 `/data/state/strimkeep.db`。从旧项目迁移时请先按 [部署说明](docs/DEPLOYMENT.md) 处理数据库文件名，不能直接覆盖旧部署后启动。

## 更新与备份

默认 Compose 使用滚动标签 `latest`。**更新不会自动发生**：请先阅读 [Releases](https://github.com/xcgtb/StrimKeep/releases) 的版本说明，并在备份数据后手动拉取、重建容器：

```bash
# 先备份 data/（建议停服务后再备份 SQLite 数据）
docker compose stop strimkeep
tar -czf strimkeep-data-backup.tar.gz data

# latest 会拉取仓库当前发布的对应镜像；固定版本需先修改 image 标签
docker compose pull
docker compose up -d
docker compose ps
```

> 切换版本前请阅读对应发行说明与迁移要求。**旧项目迁移不能直接覆盖数据目录**；详见[完整部署教程](docs/DEPLOYMENT.md)。
